Gateau Notation Sketchbook III

A 10G Ethernet / IPv4 / UDP stack, in both directions. Nothing loops back into itself here. Bytes arrive at line rate, each layer peels a header off the front, and the transmit side has to put back headers that describe data it hasn't seen yet.

source: alexforencich/verilog-ethernet (MIT, 64-bit datapath modules) RX: eth_phy_10g_rx_if → axis_baser_rx_64 → eth_axis_rx → ip_eth_rx_64 → udp_ip_rx_64 status: mockups, not generated

Why this design breaks the notation again

Studies 01 and 02 had one bus whose rows were all valid at the same rate. A packet stack has two kinds of information moving at two rates. Headers are valid once per packet. Payload bytes are valid once per bus beat, and how many beats there are depends on the packet. Parsers turn the front of the byte stream into header fields. Transmit turns fields back into bytes. So this study draws two buses: a per-packet bus on top that gains fields on the way in, and a per-beat bus below that loses bytes. Each parser is a vertical box that moves bytes from one bus to the other.

verilog-ethernet is deprecated in favour of fpganinja/taxi, but taxi's IP stack (Zircon) has no RTL yet, and taxi is CERN-OHL-S rather than MIT. The older repo is the complete one.

receive

From 66-bit blocks to UDP payload

The axis view for packets is a byte map

For a packet stack, the axis that matters is byte position, folded into beats of 8 lanes. A minimum-size frame with a 10-byte UDP payload shows everything the parsers do: where each header ends inside a beat, how far the rest has to shift, and where padding and FCS get cut.

transmit

Headers that need data that hasn't arrived yet

Transmit runs the two buses in reverse: each layer turns fields back into bytes and prepends them. The difference is timing. A header goes out before its payload, and some header fields are computed from that payload. The UDP checksum is the clear case. The RTL resolves it by holding the entire datagram in a FIFO until the checksum is known. The Ethernet FCS is computed from the data too, but it goes at the end, so it needs no buffer at all. Same kind of field, opposite cost, because of where it sits in the packet.

Glyphs added in v0.3

Everything from studies 01 and 02 still stands; these are what packet interfaces add.

Two buses

A per-packet bus (blue) above a per-beat bus (black). They move at different rates and are paired again by order.

Parse / serialise

A tall box spanning both buses. The arrow up turns header bytes into fields; down turns fields into prepended bytes.

Tail field

Valid only on the last beat: a verdict that trails the data it judges. Every consumer has to say what it does with data that already left.

Rigid region

No back-pressure is possible, because the wire doesn't wait. The block at its edge must either drop or pre-buffer.

Needed before available

A field that goes out ahead of the data it's computed from. It costs a buffer the size of the largest unit, and gateau can work out that size.

Byte map

The axis view for packets: byte position folded into beats. It shows header boundaries, realignment shifts and what gets trimmed.

What interface IP adds to the picture

  • The expensive parts are buffers, and the drawing says where they must go. Every large buffer in this stack sits at one of two spots: where a rigid region meets an elastic one (the RX and TX frame FIFOs), or where a field is needed before it's available (the UDP checksum FIFO). Both can be detected from the bus view, and the required depth follows from the maximum packet size. In compute IP the cost was in arrays and delay lines. In interface IP it's in buffering forced by timing.
  • Another latency contract, again kept by hand. The MAC delays data two blocks (input_data_d0, d1) so the CRC verdict is ready by the time the last data beat leaves, even when the FCS straddles a block boundary. It's the same ⟂ lat pattern as the DP RX parser and scrambler join.
  • Header fields can control the data. ip.length decides where the IP payload ends (it trims Ethernet padding), and udp.length does the same one layer up. So a field on the packet bus drives tlast on the beat bus. In the drawing it is a read from one bus by a box on the other.
  • Receive and transmit are coupled through state. ARP replies arrive on the receive path and fill the cache that transmit reads. A complete gateau view of an interface needs both directions on one page, connected through their shared stores.
  • This maps directly onto your DP RX. Secondary data packets and MST are packet-shaped: a header with ECC, then payload, with the header fields arriving before the data they describe. The two-bus picture and the tail-field glyph should carry over without change. The rigid region applies too, because the main link can't be stalled either.

Questions for you

  1. Should one gateau page show both directions of an interface together (as a mirrored pair sharing stores), or two pages linked through stores? The ARP coupling argues for one page. Size argues for two.
  2. For the byte map, should gateau draw a representative packet you choose (as here), or the worst cases it finds itself (largest shift, extra beat, minimum frame)? The worst cases are where the alignment bugs live.

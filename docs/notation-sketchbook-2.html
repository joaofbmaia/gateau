gateau · notation study 02

Gateau Notation Sketchbook II

The same exercise on three harder designs: an in-order core with bypasses and replays, a systolic accelerator that parks tags in queues, and a modulo-scheduled CGRA whose datapath changes shape and rate. The notation from study 01 broke in specific places, and this page fixes them.

Rocket: rocket/RocketCore.scala, integer pipeline only Gemmini: ExecuteController, MeshWithDelays, default config bubbletea: StreamingStage, float4x4 params

What changed since study 01

The DP RX link layer in study 01 was the easy case: feed-forward, fixed rate, every field moving left to right. Each of these designs forced at least one new rule. In summary, the bus view survives, but it now has a return gutter underneath, state stores on top, and every join says how its fields find each other again.

forced by Rocket

Return gutter

Back-edges (bypasses, redirects, completions) are drawn right to left in a band below the bus, never across it. The bus stays readable left to right, and the feedback is all in one place.

forced by Rocket, Gemmini

State stores with a span

Register files, scoreboards and scratchpads sit above the bus as pills stretching from their earliest read tap to their latest write tap. The span is the hazard window, and whatever covers that window (bypass, interlock, a reservation station) has to be visible somewhere.

forced by Gemmini

Rejoin kinds

Study 01's green "aligned" badge becomes one of three: ⟂ lat (equal latency, as in DP RX), ⟂ fifo (parked in an in-order queue) and ⟂ key (parked and matched by ID). Each one has a different correctness condition to check.

forced by bubbletea

Shape and rate on the row

When one payload changes shape (4 × 32 → II × 16 → 16) and rate (one per II cycles → one per cycle), that is annotated on the row and shaded, rather than turned into more rows.

forced by bubbletea

A space-time view for programmable fabrics

A CGRA's mesh is hardware plus a mapping. The bus view shows the hardware around it. The mesh itself gets the standard CGRA picture: one frame per modulo cycle, which Morpher's own _X|_Y|-T naming already uses.

kept, sharpened

Register edges named by prefix

The cycle band becomes a dashed edge at every stage boundary, labelled with the RTL's own register prefix (ex_reg_*). An elastic (valid/ready) boundary is marked » instead.

design 1 · in-order core

Rocket

Rocket's integer pipeline has about 60 pipeline registers named ex_reg_*, mem_reg_* and wb_reg_*. The bus view collapses them into eight rows: ctrl is a group row standing for the whole IntCtrlSigs bundle. The real content is underneath: three bypasses into EX, two redirects back to fetch, and a register file whose read and write taps are three stages apart.

design 2 · systolic accelerator

Gemmini

Gemmini's execute path is the best argument for rejoin kinds. In a few hundred lines, fields leave the data and find it again in three different ways. Control parks in an in-order queue during the SRAM read. The output address and ROB id park in a tag queue while the data crosses the mesh, and are matched back by matmul id. Meanwhile the PE control, valid, id and last bits ride through the mesh on the same skewed diagonal as the data.

  • Another latency contract, written as a magic number. The tag is enqueued with id matmul_id + (OS ? 3 : 2) (MeshWithDelays.scala). That offset encodes how many matmuls are in flight between issue and output in each dataflow. It is the same class of fact as the DP RX parser comment, a latency promise kept by hand. I haven't worked out the 3 versus 2 from first principles. A ⟂ key badge should show that offset, because if it's wrong, results get the wrong address.
  • The store span explains the reservation station. The scratchpad and accumulator pills are tapped by three pipelines (load, execute, store). A store with several writers and readers on different pipelines needs ordering. In this notation, that need is visible before you open ReservationStation.scala.
design 3 · your CGRA

bubbletea

Here the bus view needed the most rethinking. bubbletea's streaming stage doesn't carry a record of fields. It carries one payload that changes shape at every block: four macrostreams of 32 elements, then II micro-frames of 16 port values, then one frame per cycle into the mesh, and back again. The rows that matter are control: fire (one global enable), t (the modulo cycle, which selects a context everywhere) and the static configuration. The data row carries shape and rate annotations instead of field names.

  • The store-side latency contract lives in the bitstream. storeStreamsFixedDelay has to equal the mesh's real path latency (PE register hops plus delays) for whatever mapping is loaded, and the comment in StreamingStage.scala says so. In DP RX the contract was in RTL comments; here the compiler owns it. A gateau check on bubbletea therefore needs the bitstream (or the mapping) as an input.
  • The delayers are your largest register cost, by a wide margin. At 16 kbit against 4 kbit for the PEs, the VariablePipe array is where the area goes. Your own TODO in VariablePipe.scala about clock-gating unused registers points the same way. Whether to resize it (for example, delays shared across frames) is a design call for you. The cost view just makes it impossible to miss.
  • The bus view and the space-time view answer different questions. FIG T1 is fixed by the RTL. FIG T2 changes with every kernel. A CGRA needs both, linked: clicking the mesh box should open the frames for the loaded mapping.

Glyphs added in v0.2

These extend the vocabulary from study 01; all of those glyphs still stand.

Return gutter edge

Feedback runs right to left below the bus, labelled with what it carries. Data edges are solid; control redirects are dashed.

State store

A pill from the earliest read tap to the latest write tap. Its length is the hazard window that something must cover.

Rejoin by latency

Two paths of equal delay. Check: the latencies match.

Rejoin in order

The field parks in a queue and leaves in arrival order. Check: depth ≥ the other path's latency + 1, and nothing reorders.

Rejoin by key

The field parks and is released when an ID coming off the other path matches. Check: the ID is unique among what is in flight.

Elastic boundary

A valid/ready handshake. Back-pressure can stop here; across a plain edge, the stages move in lockstep.

Kill

A point where the transaction can be squashed. The valid row keeps going and its meaning changes.

Skew

A delay that depends on the index along an axis. Elements that must stay together pass through identical staircases.

Cyclic selector

A counter that wraps every II cycles and picks a context in every block that reads it.

Rate change

Serialise and collect. The section between them is shaded, because its rows move at a different rate.

Group row

One row standing for a bundle. It collapses by default and expands on click.

Space-time frames

For programmable fabrics: one grid per modulo cycle, with register hops between frames.

What this means for the algorithm

Three things came out of this round that change what gateau has to read, not just what it draws.

  1. Latency contracts are everywhere, and they live in different places. DP RX keeps them in comments, Gemmini in a magic offset, bubbletea in the bitstream. Every rejoin needs a declared kind and a declared latency or key. Gateau should check them, so its input is the RTL structure plus those declarations, and for bubbletea, plus a mapping.
  2. Chisel makes extraction realistic. Two of these three designs are Chisel, and their bundles (IntCtrlSigs, MeshData, ComputeCntlSignals) are exactly the rows and groups the drawings use. Reading elaborated Chisel (FIRRTL) for structure, with a small annotation file for contracts, looks like the right first source. Rocket's pipeline-register naming (ex_reg_*) even gives stage boundaries for free.
  3. The views should be linked, not separate. Bus view at the top level; gutter and stores always on; cost and contract as overlays; axis view, skew and space-time frames opened by clicking into a box. That is tsncd's forms toggle, extended with zoom.

Questions for you

  1. For bubbletea, should gateau read Morpher's mapping output directly, or the bitstream your assembler produces? The bitstream is closer to the truth, and the mapping is closer to the intent.
  2. Is FIRRTL / CIRCT the extraction source you want, or would you rather annotate designs by hand at first (a small DSL, as planned) and add extraction later? My leaning: hand-written DSL first, and FIRRTL once the notation is stable.
  3. Rocket's frontend, Gemmini's reservation station and bubbletea's streaming engine are all collapsed into single boxes here. Each is a design of its own. Which one would you want drawn next?

Gateau Notation

The consolidated set of abstractions behind studies 01–03, and a method for drawing any architecture with them. Eight primitives, four views, eight derived checks, and one rule for which visual channel means what.

consolidates: study 01 (DP RX) · study 02 (Rocket, Gemmini, bubbletea) · study 03 (Ethernet) applied in: study 04 (DP RX, all views) · study 05 (invented MST receiver) status: draft for review

Changes in v1.2

An invented multi-stream receiver (study 05) tested what v1.1 couldn't draw: items routed apart and merged back. That added one primitive and two attributes.

new primitive 8

Route and merge

Route sends each item, or part of one, to one of K carriers by a selector. Merge combines K carriers into one under a policy. Both declare a granularity. Drawn as a fan and a funnel.

carrier attribute

Indexed carriers

A carrier replicated by an index (ssym[sid] ×4), drawn as a deck. Stages and clock domains can carry the same index.

state attribute

Epoch

Double-buffered state that switches at a point defined by the flow. Every reader must switch at that point.

Changes in v1.1

Drawing the DP RX model (study 04) exposed three gaps. All three are now part of the notation.

grammar

Boundaries are named

Boundaries get names (b0, b1 = b0 + 1), and stages are placed between them instead of carrying their own latency. Two branches between the same pair of boundaries are equal-latency by construction, so a lat join becomes a structural fact of the model. What remains to check is whether the RTL agrees with the declared boundary latencies.

layout

Stubs for distant state

A read of out-of-flow state whose tap would cross more than one carrier band is drawn as a stub: a short tap ending in a labelled tag (cfg.bpc · vcfg). Reads that cross at most one band stay as full taps.

honesty

The ≈ marker

Any mark that drops detail present in the model carries ≈, with the omission stated in the caption. A diagram can simplify, but it must say where.

The model in one sentence

An architecture is a set of items flowing left to right on carriers, through stages that read, write, create and consume the items' fields, across boundaries that set latency and flow control, alongside state the stages tap, with feedback running back underneath. Carriers can be routed into indexed copies and merged back.

Every glyph from the studies is either one of the eight primitives below, an attribute of one, or something computed from them. Over the three studies the glyph count grew to about thirty-five. Most of that growth came from drawing the same idea twice. A rate change in bubbletea and a header parser in Ethernet are the same thing. So are a cycle band, an enable region and a line-time region, and so are DP RX's latency badge, Gemmini's tag queue and the MAC's CRC hold.

Eight primitives

These are the things an author declares. The tag under each card says which studies forced it.

1

Carrier

A stream of items at one rate. An item is whatever counts as "one": a symbol pair, an instruction, a matmul row, an II-period, a packet, a beat.

attributes
item name · rate · parent carrier (rates nest: packet ⊃ beat, II-period ⊃ cycle) · index (×K copies, one per stream)

Field

A named value carried by every item of a carrier, between the stage that creates it and the stage that consumes it.

Stage

An operator on items. Its relation to each field is one of four: reads, writes, creates, consumes. A stage spanning two carriers transfers values between them.

attributes

Boundary

The edge between two consecutive stages. It holds the timing of the design: how long, and who can stop whom.

attributes

Fork and join

Where one item's fields take different paths and later have to meet again. Every join declares how the parts find each other.

Route and merge

Where different items part ways or come together. A route sends each item, or part of one, to one of K carriers. A merge combines K carriers into one.

One channel, one meaning

The studies reused the same visual channel for unrelated things. For example, dashes meant five different things and blue meant four. The fix is to give each visual channel exactly one job. When something new needs drawing, it gets an attribute of an existing primitive and a channel nobody is using, not a new glyph.

Four views of one model

Following tsncd, views are renderings of one model rather than separate drawings to keep in sync. The bus view is the map; the others are reached from it.

primary

Bus view

Carriers as bands, stages as boxes, state on top, feedback in the gutter. Every design gets one. Collapsed groups and closed boxes keep it under about a dozen rows.

zoom into a field or stage

Axis view

A field's axes drawn as wires, with NCD's operators: broadcast, index, copy, reduce, reshape, permute, skew, realign. The byte map (axis = byte position folded into beats) and space-time frames (axes = PE grid × modulo time) are two layouts of this one view.

zoom into a boundary or join

Time view

A cycle grid of items × cycles around one join or region. It is the picture for a contract: aligned versus skewed, a FIFO filling, a stall propagating.

overlay on the bus view

Overlays

Contracts (badges with results), cost (row thickness = bits, buffers as bars) and domains (hue). Each can be switched on or off without changing the layout.

Worked redraw: bubbletea in v1

Study 02 drew bubbletea with a shaded rate band and fire, t and cfg as rows. Under v1, the two rates are two carriers, and the remap and collect steps become transfers between them, exactly as Ethernet's parsers are. Configuration and the modulo counter move up to state, and fire becomes a lockstep group fed by flow feedback. Nothing new had to be invented: the same seven primitives cover a CGRA's streaming stage and a packet parser.

The method

The order matters: most bad architecture diagrams start by drawing boxes. This method starts by deciding what flows.

  1. Name the item. What is "one thing" moving through the design? If there is more than one answer at different rates (packet and beat, II-period and cycle, matmul and row), each answer is a carrier. Nest them coarse above fine.
  2. List the stages in flow order along each carrier. Mark stages that span two carriers as transfers.
  3. Name every boundary and give its latency relative to another (b1 = b0 + 1, "variable", or "?") and its coupling: lockstep, elastic or rigid. Place each stage between two boundaries. Note clock domains. Write "?" rather than guessing; unknown latencies are where contracts hide.
  4. Enumerate fields per carrier. For each one: type in axis terms, the stage that creates it, the stages that read and write it, the stage that consumes it, and whether it is available for the whole item, at its head, or at its tail. Group bundles.
  5. Find forks and joins. Wherever an item's fields split and meet again, declare the join discipline (lat, fifo, key) and its parameter.
  6. Find routes and merges. Wherever different items part ways or share a carrier, declare the selector and default (route) or the policy and the field that keeps origins apart (merge), and the granularity of each.
  7. List state. For each store: taps, writer kind (in-flow, out-of-flow, shared), and whether it is cyclic.
  8. List feedback: bypasses, redirects, kills, ready/stall, and anything leaving the design (bitslip, reset requests).
  9. Run the five checks. Every failing or undeclared one is a finding, and usually the most valuable output of the exercise.
  10. Lay out by these rules: carriers coarse to fine, top to bottom; rows inside a carrier ordered by the stage that creates them; state above, ordered by span with the shortest nearest the bands; gutter edges ordered by span with the shortest nearest the bands; at most about twelve rows per view, collapsing groups and closing boxes to stay under it; any out-of-flow read crossing more than one band becomes a stub; any simplification gets ≈.
  11. Zoom where shapes change. Every stage that reshapes, permutes, skews or realigns a field gets an axis view. Every join with a non-trivial discipline gets a time view.

The model as text

If the abstractions are right, an architecture should be describable in a few lines without any drawing. This is a sketch of what a model file could look like, not a syntax proposal. Here is the DP RX link layer from study 01:

carrier sym  "symbol group per lnk_clk"   axes ℓ = P_LANES, s = P_SPL
carrier msg  "message"                    # the control ring is its own carrier

field sym.k, sym.dat : bit[ℓ,s], u8[ℓ,s]
field sym.lock       : bit
group sym.tag        : {sol, eol, vid, sdp, msa, vbid} : bit[ℓ,s]

state cfg  out-of-flow {lnk_en, lanes, scrm_en, mst_en, bpc}   written by CTL from msg
state ila  in-flow     lanes aligned                           written by TRN

boundary b0                        # TRN output
boundary b1 = b0 + 1

stage TRN   ×ℓ; writes k, dat; writes ila;        taps msg
fork  raw  = {k, dat}
stage PARS  between b0 → b1; reads raw[ℓ = 0]; creates tag.*; requires ila
stage SCRM  between b0 → b1; ×ℓ; writes k, dat; creates lock = ∧ℓ; reads cfg
join  lat(PARS, SCRM)                              # by construction: both b0 → b1
stage MSA   reads k, dat, tag.msa; consumes tag.msa; emits msg
stage SDP   if P_SDP; reads k, dat, tag.sdp; consumes tag.sdp; emits sdp_out @ sdp_clk
stage VID   consumes all; emits video @ vid_clk     boundary rigid → elastic via FIFO

About twenty lines hold everything FIG B of study 01 shows, plus the check that study 01 could only state in prose. The full model, with modes, carriers and checks, is docs/models/dprx.gateau.

Not yet covered

These showed up in the designs but are only sketched in the notation. Modes have now been tried once (study 04) and worked; the rest are untested.

  • Merge fairness. v1.2 checks identity and atomicity, but not starvation: fixed priority can starve an input, and checking it needs rates the model doesn't have yet.
  • Replicas that differ. An indexed carrier assumes all copies are the same. Stream 0 with audio and the rest without would need per-index exceptions.
  • Modes. DP RX training versus normal operation, bubbletea configuring versus computing. A likely answer is that the bus view is drawn per mode, with stages and fields marked by the modes they exist in. This hasn't been tried.
  • Out-of-order completion. Kill covers in-order squashing. A reorder buffer is a key join over many items at once, and the notation hasn't met one yet.
  • Clock-ratio carriers. Two carriers in different domains at a fixed ratio (a 2:1 gearbox, DDR) might be nested carriers rather than a CDC. This is a guess so far.
